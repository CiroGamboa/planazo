# 0019 — Per-user message serialization at the dispatch layer

- **Date:** 2026-07-29

## Context

`bot/app.py::build_application` registers five `CommandHandler`s and one `MessageHandler` (`bot/chat.py`'s three-way dispatch: registration continuation, register-first notice, or `planazo.agents.event_agent.run_once` off-thread). Every one of those six handlers reads and writes state scoped to one Telegram sender: `users.pending_registration_field` (ADR 0013), the four registration-profile columns, `preferences` rows, and the sender's private `var/memory/*.jsonl` facts (ADR 0004). None of that state is protected against two overlapping runs for the *same* sender.

**PTB already serializes everything, which is the actual bug.** `ApplicationBuilder`'s default `concurrent_updates` is `1` (verified against `python-telegram-bot` 22.8's `ext/_applicationbuilder.py:1071-1074`, mapped onto `SimpleUpdateProcessor(1)`). With `max_concurrent_updates == 1`, `Application.__update_fetcher` does not create a task per update at all — it `await`s `__process_update_wrapper(update)` directly in the fetcher loop (`ext/_application.py:1216-1220`), so the *next* update is not even pulled off `update_queue` until the current one's handler coroutine has returned. That includes every internal `await`, `asyncio.to_thread` included. So today, one user's multi-second `run_once` call blocks *every other user's* bot interaction too — not just their own next message. This ticket's problem statement ("Users are independent — one user's slow run never delays another's") requires *raising* `concurrent_updates`, which is the opposite of what current code does, and that raise is what turns the intra-user race the ticket names into a reachable bug for the first time (today, the race exists in principle but PTB's `concurrent_updates=1` happens to be an accidental global lock that also prevents it in practice).

**The per-user key must be `telegram_user_id`, not `chat_id`.** The obvious shortcut — lock on `message.chat_id`, which `bot/surface.py::surface_for` already binds the reply channel to — is wrong. `tests/test_bot_app.py` and `bot/commands.py:210` already exercise and document the `/prefs@botname` form "Telegram delivers in group chats," so the bot's own command-routing layer is not written for private 1:1 chats only; `Message.chat_id` and `Update.effective_user.id` are independent identifiers that coincide only in a private chat. Neither ADR 0011 nor `docs/PLANAZO-PROJECT-CONTEXT.md` states a private-chat-only constraint anywhere (checked: no "1:1", "personal chat", "direct message", or "group" restriction in either document). The state this ticket protects — `pending_registration_field`, the profile columns, `preferences`, private memory facts — is keyed by the internal `users.id`, itself resolved from `telegram_user_id` (`bot/session.py::resolve_user`), never from `chat_id`. A per-chat lock would incorrectly serialize two unrelated senders who happen to share a group chat, and would not protect a sender who somehow reaches the bot through two different chats. `telegram_user_id` is available on `IncomingMessage` with no database read, so keying on it costs nothing extra at the dispatch layer.

**Alternatives considered.**

- **A per-chat lock** (`chat_id`). Rejected on the group-chat evidence above: it serializes unrelated senders against each other in a shared chat (violating "users are independent"), and it keys on the wrong identity for the state actually being protected.
- **A single global worker** processing every update for every user, one at a time. Trivially correct for per-sender ordering — a total order is a superset of a per-sender order — but reintroduces exactly the cross-user stall this ADR's `concurrent_updates` change is meant to remove. Rejected: it satisfies AC1 (per-sender FIFO) but fails AC2 (cross-user independence) by construction.
- **An external broker** (Redis, Celery, any persistent/cross-process queue). Rejected per the ticket's own scope: one bot process, in-memory; a broker adds a network hop, an operational dependency, and durability semantics ("survive a restart") this ticket explicitly disclaims ("messages pending at shutdown are lost" is accepted, not a gap to fix).
- **A per-user `asyncio.Queue` plus a dedicated worker task per active sender**, spawned on that sender's first message and torn down once their queue drains. Also correct, and the mechanism the ticket's own Notes section names as the other option. Rejected in favor of the mechanism below for one reason: a detached worker task needs its own lifecycle management (spawn-on-first-item, exit-on-drain) and its own error-propagation path, because an unhandled exception in a task nobody `await`s is silently dropped by asyncio unless something explicitly retrieves it. The mechanism below has no such task — the coroutine that already exists for this update (the one PTB itself creates and manages once `concurrent_updates > 1`) is the one that runs the job, so an unexpected exception propagates to code that already has an error path (PTB's own `process_error`), and there is no separate task lifecycle to get wrong.
- **A per-user `asyncio.Lock`** (the first shipped design). Rejected after review caught a real ordering bug: `asyncio.Lock`'s FIFO guarantee is about the order coroutines *join its internal waiter queue* (the moment `acquire()` actually runs), not the order `dispatch()` was called. The first implementation awaited the caller's immediate acknowledgment (`on_enqueued()` — a real network call with variable latency in production) *before* joining the lock's wait queue, so two already-queued messages for the same sender could run out of arrival order whenever the second message's acknowledgment resolved faster than the first's. Replaced before merge by the deque-of-events mechanism below, which reserves a caller's FIFO position synchronously, before `on_enqueued()` is ever awaited — making arrival order depend only on call order, never on acknowledgment latency.

## Decision

**A per-user FIFO gate plus a bounded per-user waiter count, keyed by `telegram_user_id`, wraps every handler dispatch in `bot/app.py::adapter_for` — and `concurrent_updates` moves from PTB's default of `1` to `True` (PTB's own "no cap" spelling, `256`) in `build_application`.** The two changes are inseparable: raising `concurrent_updates` alone reintroduces the intra-user race this ADR exists to close; adding the per-user gate without raising `concurrent_updates` changes nothing observable, because PTB's own default already serializes every update system-wide.

**Mechanism** (`planazo.bot.queue.PerUserQueue`, new module, PTB-free — no `telegram` import, consistent with every module in `bot/` except `app.py`/`surface.py`):

- Per `telegram_user_id`: a `busy` flag, an integer *waiting* counter (messages accepted into the queue but not yet running — **not** including the one currently in flight), and a `deque` of "turn" events — all created lazily on first use and never evicted (the `users` table already grows one row per sender for the lifetime of the process, so this adds no new unbounded-growth axis).
- `dispatch(key, job, on_enqueued)`:
  - If the key is not busy: mark it busy, run `job()`, return `RAN`. No busy-check-then-act sequence here crosses an `await`, so there is no race window between "check not busy" and "commit to running now."
  - Else, if the waiting counter is already at the configured bound: return `OVERFLOW` immediately. `job` and `on_enqueued` are never called; the message is dropped, not queued.
  - Else: **synchronously**, in the same stretch of code as the busy check — before anything is awaited — append a fresh `asyncio.Event` to the key's `deque` (reserving this call's FIFO position) and increment the waiting counter. Only after that reservation does it `await on_enqueued()` (the caller's immediate acknowledgment — sent before this call's turn arrives, which is what makes it *immediate* rather than delivered after waiting), then `await` its own turn event. Because the reservation happens before `on_enqueued()` is ever awaited, two calls for the same key run their jobs in the order they were *called* in, regardless of how long either call's `on_enqueued()` takes to resolve — the property the rejected `asyncio.Lock` design above did not actually have. Once this call's turn event is set, it decrements the waiting counter (it is no longer "waiting" the moment it begins running), runs `job()`, and returns `ENQUEUED`.
- A job that raises still hands the key off to the next waiter (or frees it, if there is none) — that handoff runs in a `finally` block regardless of how `job()` exits — so the next waiter for that key still runs. This is the crash-recovery guarantee. The exception itself propagates out of `dispatch()` to whatever called it (the per-update task PTB itself created, once `concurrent_updates > 1`), unchanged from today's handling of any handler exception PTB's own `process_error` already covers.

**The bound and the two message ids come from `data/bot.yaml`.** `BotConfig` gains a required `queue: QueueConfig` section (`bound: int > 0`, `ack_message`, `overflow_message` — both cross-validated as keys of `messages`, mirroring how `registration.steps[].prompt` is validated today). The bound counts *waiting* messages, not the in-flight one: a bound of 10 admits 1 running + up to 10 queued before the 12th arrival overflows.

**The acknowledgment and overflow replies resolve at `config.default_locale`, not the sender's stored locale.** This follows the precedent `adapter_for`'s existing `edited_command` refusal already sets: both fire before a database connection opens (the queue decision happens on `IncomingMessage` alone, deliberately before `resolve_user` runs), so there is no `UserRecord.language` to read yet without paying for a throwaway connection just to look it up.

**Every handler dispatch goes through the same queue instance.** `build_application` constructs exactly one `PerUserQueue`, passed explicitly into all six `adapter_for(...)` calls — the five commands and the plain-text `MessageHandler`. A sender's `/prefs set` and their next free-text turn serialize against each other, not just two free-text messages against each other, because the hazard (`pending_registration_field`, the profile columns, `preferences`) is not specific to any one handler.

## Consequences

### Positive

- **The actual bug (system-wide serialization) is fixed, not papered over.** Raising `concurrent_updates` is what makes "one user's slow run never delays another's" true; today it is false regardless of anything this ticket adds on top.
- **No new task lifecycle to manage.** The coroutine PTB already creates per update is the one that runs the job; there is no separate worker task that could leak, get cancelled without cleanup, or drop an exception silently.
- **Cross-handler correctness for free**, not just cross-message: `/prefs`, `/register`, and free text serialize against each other for the same sender, because the queue wraps dispatch itself, not any one handler's body.
- **No compatibility-surface change.** `data/bot.yaml` is a committed, from-scratch-validated config file, not accumulated user data — adding a required `queue:` section is a same-commit YAML edit, not a migration.

### Negative / accepted trade-offs

- **Cross-user SQLite write contention becomes reachable for the first time.** With `concurrent_updates=1`, two different users' writes could never overlap; with `concurrent_updates=True`, they now can, and `storage/db.py::connect()` relies on `sqlite3`'s default 5s connect timeout with no explicit `PRAGMA busy_timeout` or WAL mode. Filed as [#96](https://github.com/CiroGamboa/planazo/issues/96) — not blocking, since this bot's expected traffic makes true overlapping writes rare, and the per-user hazard this ADR closes is the one #58 actually asks for.
- **The acknowledgment and overflow replies cannot honor a sender's stored locale.** Accepted: the alternative (a throwaway connection at dispatch time just to read `language`) duplicates work the queued job already does, and the existing `edited_command` precedent already accepts the same trade-off.
- **256 is a cap, not truly unbounded.** `ApplicationBuilder.concurrent_updates(True)` maps to `SimpleUpdateProcessor(256)`, not an unlimited number of concurrent PTB-level tasks. Accepted: 256 concurrent *distinct senders* is far beyond this bot's expected personal-project load, and this ADR does not add a second, smaller cap of its own — the per-user gate is the only limiting mechanism this ticket introduces, matching the ticket's own "no global concurrency cap" out-of-scope line.
- **A `busy` flag and a `deque` of turn events are allocated per sender for the life of the process and never freed.** Accepted at MVP scale (matches the existing one-`users`-row-per-sender growth curve); revisit only if sender count ever approaches a level where this matters, which is far outside this bot's current scope.
