What is Planazo?

A user asks in natural language for events matching a time window and interests. Planazo interprets the intent, retrieves candidates from a validated catalog, ranks them, and returns a bounded answer.

Three agents, three jobs

Recommender

  • Does: answers a user query, ranks events, returns a bounded response
  • Runs: every user turn (bot / CLI)
  • Tools: search_events, memory (retrieve / save), ask_user

Extractor

  • Does: turns a raw Instagram post into validated event rows
  • Runs: on-demand from the scheduler
  • Tools: fetch_instagram_post, save_event, report_extraction_status

Curator

  • Does: soft-deletes stale events, merges dupes, fixes categories
  • Runs: daily cron
  • Tools: six catalog read + write tools, admin-scoped

All three run on typed LangGraph StateGraphs — ADR 0023 (Recommender), ADR 0024 (Extractor).

Memory tools are closures over user_id — the LLM can never point them at another user (ADR 0004). No tool the Recommender exposes today is irreversible or externally visible.

RAG — what and why

Retrieval-Augmented Generation: fetch relevant events at query time, hand them to the LLM as grounded context.

Before RAG

Category filter only. "recital at Palau de la Musica" → nothing matches "recital" as a category.

With RAG

Hybrid semantic + lexical search. Finds the classical-chamber-music event at Palau even without keyword overlap.

ADR 0025 — hard filters (category, city, date) still gate the candidate set before RAG ranks within it.

RAG — corpus & chunking

Sources

  • SQLite events table at var/planazo.db
  • Populated by: scripts/seed_events.py (60 demo events) + Extractor (Instagram, when live)
  • Separate eval corpus at data/eval/events_seed.jsonl — 120 events

Chunking

  • One chunk per event — the row is the atomic semantic unit
  • Chunk ID = event ID (no resolver needed)
  • Chunk text: title. description. Venue: … Category: … Tags: … Time: … Price: …
No overlap, no windowing. Events are small; splitting one across chunks would lose the join between title + venue + time.

Eval — RAG retrieval

20 golden queries on the 120-event corpus. rerank = on.

khit@kprecision@krecall@kMRRnDCG@k
11.0001.0000.6901.0001.000
31.0000.5560.8751.0000.967

Reranker lifts MRR from 0.944 → 1.000 — the first golden hit consistently lands at rank 1 once the cross-encoder runs.
hit@k = "any golden in top-k". precision@k drops as k grows because there is a fixed number of golden events per query. Recall@k rises to 1.0 by k=10.

Eval — RAG generation (LLM-as-judge)

Same 20 golden queries. Judge = OpenCodeJudge (cheap model), cached per (metric, case_id, answer_hash).

0.985 Faithfulness (rerank on)
0.333 Answer relevance (rerank on)
0.693 Context precision (rerank on)
Faithfulness is high — the model does not invent facts. Answer relevance is a real weakness: the model retrieves well but summarises loosely.
Answer relevance = "does the answer address the user's question". Faithfulness = "does it stick to the retrieved chunks". They can diverge — a factually grounded answer can still miss the ask.

Eval — Agent trajectory

12 scenarios × 3 runs at temperature = 0.7. Threshold: tool_selection ≥ 0.5.

2 / 12 Reliable (pass^3)
2 / 12 Flaky (pass@3, not pass^3)
8 / 12 Hard-fail (pass@3 = no)
T=0 gives the same answer 3×; T=0.7 exposes real variance. pass^3 ("all 3 pass") is the actual reliability signal — pass@3 alone is optimistic.

Metrics: tool_selection_accuracy · trajectory_precision · trajectory_recall · goal_completion (LLM-judge).

Hard-fail cases show error_type=search_not_completed — the LLM decided not to call search_events. Real product signal, not a scorer bug. Next iteration should tune the prompt or add a stricter tool-forcing policy.

Tools ≠ outcome

Trajectory metrics grade what the agent did. goal_completion grades what the user saw. They can disagree.

tell-me-more-about-2
1.0 tool_selection / precision / recall 0.0 goal_completion

Called the right tool. But "#2" refers to a prior turn that the eval harness doesn't thread — the answer couldn't satisfy the ask.

first-date-ambiguous
0.0 tool_selection / precision / recall 0.767 goal_completion

Skipped the expected clarification. But the direct answer still satisfies "recommend something for a first date".

Safety — 4 attacks × 4 defense layers

Attack Caught by How
direct-injection Layer 1 — input filter Regex: "ignore previous instructions…"
tool-abuse Layer 1 — input filter Regex: "call ask_user with…"
exfiltration Layer 1 — input filter Regex: "print everything user 2…"
indirect-injection Layer 2 — structural (cited) Retrieved text never enters the system role — ADR 0004
4 / 4 Attacks caught
0 / 36 False positives on legitimate traces
2 + 2 Live layers · cited layers

Layer 3 = output filter (secret patterns). Layer 4 = capability constraints (memory closure, approval gate). Cited to ADR 0002 + 0004 — invariants live once.

Recap

  • Agents — 3 LangGraph state graphs (Recommender, Extractor, Curator), typed boundaries at every tool.
  • RAG — hybrid dense + BM25 with RRF fusion, then cross-encoder rerank. One chunk per event.
  • Eval — retrieval + generation metrics (HW3) plus tool_selection + trajectory + goal_completion (HW4).
  • Reliability — pass^3 at T=0.7 exposes flakes that pass@3 hides.
  • Safety — 4/4 attacks caught, 0 false positives, 2 layers live + 2 cited.
  • Observability — every run is an MLflow trace with three join-key tags.

uv run python scripts/seed_events.py                          # 1. seed 60 events into var/planazo.db
uv run planazo-agent-eval --runs 3 --temperature 0.7          # 2. 12 × 3 = 36 traces + pass@3 / pass^3 table
uv run python scripts/run_trace_scorers.py                    # 3. attach scorer feedback to every trace
uv run python scripts/run_safety_batch.py --run-attacks --force-trace  # 4. 4 attacks + FP count
